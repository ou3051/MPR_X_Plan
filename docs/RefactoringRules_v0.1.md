# 重构规则 v0.1

文档状态：草案
版本：v0.1
日期：2026-05-07

## 1. 重构目标

- 提升代码可读性、可维护性和可测试性。
- 重构必须保持现有业务行为、数据语义和用户可观察结果不变。
- 不得借重构引入新功能、改变默认参数、调整交互流程或修改错误码语义。
- 每轮重构必须有明确目标、范围、风险、验证命令和提交边界。

## 2. 架构边界

- `measurement_core` 必须保持独立，不依赖 Qt、VTK、DCMTK 或 CUDA。
- 外部库类型不得出现在 core public headers 或公共 domain 数据结构中。
- DICOM、MPR、DRR、planning、persistence、app 各模块职责不得混入无关模块。
- UI 层可以编排业务流程，但可复用算法、几何、序列化和校验逻辑应优先沉到对应 measurement 模块。
- 公共接口变化必须同步更新 `docs/PublicInterfaces_v0.1.md` 和相关单元测试。

## 3. 清理规则

- 优先移除确认未使用的函数、类型、声明、include、局部变量和旧 UI handler。
- 优先清理开发期遗留内容，包括本机硬编码路径、测试期窗口标题、临时调试文案和不可达分支。
- 删除前必须通过跨文件搜索确认没有调用点；仅凭名称像“unused”不足以作为删除依据。
- 对仍被调用但命名不佳的代码，优先重命名或局部整理，不得把可用行为当作死代码删除。
- 不删除启动 phantom、错误回退、兼容路径或测试夹具，除非已有等价行为和测试覆盖。

## 4. 拆分规则

- 超过 2000 行的文件必须先审查并清理遗留代码，再考虑结构拆分。
- 拆分应围绕单一职责进行，例如 UI 构建、交互处理、渲染适配、数据加载、序列化映射。
- 拆出的类或 helper 必须有清晰所有权边界，不引入隐式全局状态。
- 保持现有 target 和模块依赖方向，除非重构目标明确要求调整 CMake。
- 搬移代码时优先保持函数签名和调用顺序稳定，降低行为漂移风险。

## 5. 可读性规则

- 命名遵循 `docs/CodingStandards_v0.1.md`。
- 函数应短小、单一意图；复杂流程优先拆成命名清晰的局部 helper。
- 使用早返回降低嵌套层级，但不得牺牲错误处理完整性。
- 条件判断应表达业务含义，避免把同一组魔法值散落在多个位置。
- 注释只解释非显然意图、约束或算法背景，不重复代码表面含义。

## 6. 可维护性规则

- 跨模块错误继续使用 `Result<T>` 或 `Result<void>`，不得用异常传递业务错误。
- 错误码必须稳定，新增跨模块错误码优先固化为 core 常量。
- 数据流应显式传递，避免新增隐藏状态、单例或环境依赖。
- 重复逻辑达到可读性或维护风险阈值时再抽象，不为单次使用过度抽象。
- 重构中发现真实缺陷时，应单独记录并作为后续修复任务处理，除非不修复会阻塞本轮重构验证。

## 7. 测试规则

- 代码重构前后必须至少通过 Debug build 和 CTest。
- 纯搬移或死代码删除应保持现有测试结果一致。
- public API、错误路径、坐标几何、DICOM tag/HU、DRR、工程包序列化相关变化必须补充或更新 GoogleTest。
- UI-only 整理至少要保证编译通过，并保留现有交互入口。
- 如果某项测试被跳过，必须在结果说明中标注跳过原因。

## 8. 执行流程

1. 扫描目标文件的行数、职责、依赖和调用点。
2. 列出可删除遗留代码、可局部整理代码和需要单独拆分的代码。
3. 先做最小安全清理，再做结构拆分。
4. 每个重构批次完成后运行：

   ```powershell
   cmake --build D:\code\codex-MPR_DRR\build --config Debug --parallel
   ctest --test-dir D:\code\codex-MPR_DRR\build -C Debug --output-on-failure
   ```

5. 提交前检查 `git diff`，确认没有混入无关格式化、生成文件或行为改动。
6. 提交说明应描述重构目的、范围和验证结果。

## 9. 当前重构优先级

1. `src/app/MprPlanVerificationWindow.cpp`：先清理确认无用的遗留代码，再拆分 UI 构建、MPR 交互、DRR 交互和仪器编辑逻辑。
2. `src/measurement/dicom/src/DicomVolumeLoader.cpp`：分离 tag 读取、slice 排序、几何校验和 `VolumeData` 构造。
3. `src/measurement/persistence/src/ProjectManifest.cpp`：分离 JSON 读写、domain mapping 和错误构造。

## 10. 准入检查表

- 是否明确本轮重构目标和非目标？
- 是否确认没有改变业务行为或用户可观察结果？
- 是否保持模块依赖方向和 public API 文档同步？
- 是否删除前完成跨文件引用检查？
- 是否运行并记录 build 和 CTest 结果？
- 是否避免提交无关文件、生成物和纯格式化噪声？
